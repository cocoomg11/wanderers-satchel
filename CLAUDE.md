# CLAUDE.md: Wanderer's Satchel

Foundry VTT module (v13/v14, any game system): a GM hub for the user's other modules. One window with a sidebar: Overview, a page per module (version, active, update check, health, open its panel / docs / issues), Tools pages, a combined health check with Fix buttons, one-file settings export/import for all, settings backups, What's new after updates, one debug-logging switch, a registration API. Every module stays standalone: the Satchel never duplicates their settings or windows. Public repo, MIT.

## File map (`scripts/`)
- `main.mjs` entry: feature settings, the settings menu, key binding (core `registerOpenKeybinding`, action `open`, none by default), `registerWindowPlacement`, `hideDataFolder` (shown = our `showModuleData`), scene control + Settings sidebar buttons, the API (`game.modules.get("wanderers-satchel").api`, set in `init`), hook `wanderers-satchel.ready` in `ready`.
- `core.mjs` binds the vendored wanderers-core 0.5.1 (`vendor/wanderers-core/`, pin `wanderers-core.lock.json`): `F` (createFeatures), `S` (createSettings: `debugLog`, client `showModuleData`), `log`/`warn`. `features-model.mjs` (pure) the feature list and settings rows. `features.mjs` thin wrappers (`FEATURES`, `on`, `need`, `registerSettings`).
- `const.mjs` id, title, hook names; re-exports core's `esc`/`plural`/`plain`.
- `registry-model.mjs` (pure) registration reading, adapter/registration merge, card model, doc links, debug plan. `registry.mjs` live registry, `openPanel` fallbacks (entry → first settings menu → SettingsConfig), window refresh.
- `adapters.mjs` built-in adapters (toolkit, Ringmaker, Loot Ledger, Red Book). `apiOf` returns null on non-GM clients. `adapters-model.mjs` (pure) skip lists, import validators (toolkit `flightNetwork`), Ringmaker status → lines, Loot Ledger state → sections, dependency lines.
- `version-model.mjs` (pure) version compare (from core), `manifestFor` (own manifest, else GitHub project URL → its latest release manifest), `repoOf`, update source (GitHub manifest → REST latest release, since release asset redirects have no CORS), cache (session storage), timeout, `checkUpdate`.
- `store-model.mjs` (pure) the GM-only store: `normalizeStore` (core `versioned`, v1: `seen`, `backed`, `updateBackup`, `snapshots` ≤5, each ≤1 MB of JSON text), `changes` (core `decide` per module), `makeSnapshot`, `addSnapshot`/`removeSnapshot`, `updateSetKey`, `REASONS`. `store.mjs` (0.6.0) a thin wrapper over core `createStore(ID, { name, flagKey: "store", entryFlag: "storeEntry", normalize: normalizeStore, about, log, isWriter })`: the journal ("Wanderer's Satchel (GM only)", ownership None, found by `storeEntry`, in core's "Module data" folder), `entry`/`read`/`update(fn)`/`file()`/`remove()`/`status()`, `isWriter()` (active GM). `Life.onReady` calls `Store.file()` once on the writer.
- `notes-model.mjs` (pure) What's new: `notesSource` (manifest `changelog` in the module folder / raw GitHub, else GitHub releases REST), `parseChangelog` (## version headings), `between`, `releaseSections`, `fetchNotes` (never throws), `markdownHtml` (escape everything first, then a small subset: headings, lists, bold/italic, code, http(s) links).
- `lifecycle.mjs` daily check (localStorage `wanderers-satchel.updateCheckedAt`, once a day per browser), backups (`takeBackup`, `backupForUpdates`, `onSetup` reads in setup / written in ready), What's new (`scanNews`, `news`, `dismiss`), `onReady`.
- `self-model.mjs` (pure) the Satchel's own health lines with `satchel:*` fix ids; `self.mjs` its entry (`ENTRY`, not in the sidebar, last group of the combined report) and `runFix` (any module's fix: own `run` or registration `fixes[action]`, optional DialogV2 confirm).
- `health-model.mjs` (pure) report normaliser, time limits (`healthTimeout`: 90 s first run, then max(30 s, 3 × last), cap 5 min), `runChecks` (all at once, independent; states pending/slow/timeout/ran/failed; late answers replace the timeout), grouping + summary. `health.mjs` live runner + window that redraws as results come in.
- `settings-model.mjs` (pure) bundle around core's settings file (`buildExport`/`readImport` with validators), `plainJson`, `validatorsFor`, `recheck` (write-time check), size limits. `settings-io.mjs` export, `pickFile` (returns `{ name, size, text | error }`, errors shown inline), `readText`, `apply`; only hub entries and the Satchel are read/written. The preview is the hub's Settings transfer page.
- `hub-model.mjs` (pure) `dataFolderModel` (0.6.0: Maintenance's Module data panel), page router (`overview`, `module:<id>`, `health`, `transfer`, `backups`, `maintenance`; unknown module or feature off → overview), `backupsModel`, `whatsNewModel`, sidebar key moves, `healthIndex` (from `health.mjs` `latest()`), dots, update/health badges, view models for nav / overview / module page / import preview (ticks as a Set of `"i:j"`). `hub-view.mjs` (pure) HTML per page on core's `wc-*` classes and helpers, the health report (`healthHtml`: filter chips, hidden-module note, `card` wrapper), `filterBar`, `button`, `badge`/`icon` (core's; no ✓ ⚠ ✗ characters). `filter-model.mjs` (pure) the health filter; `prefs.mjs` its localStorage key.
- `hub.mjs` `HubApp` (`RememberedWindow(ApplicationV2, { key: "hub" })`, 1000×720, `actions` for every click, static `TABS` + `tabGroups` + `changeTab` for Export / Import), `refresh()` redraws sidebar + page in place (not Maintenance/Transfer, to keep typed input and ticks), update checks, debug-all, `open(page)`, `openImport()`. `health.mjs` keeps `latest()` results from every run and `onResult` listeners (the hub dots); `HealthApp` (`RememberedWindow`, key `health`) stays for `api.health({ window: true })`. `cleanup.mjs` Remove Satchel data (`plan`, `remove`, `submit`, `counts`; rendered on the Maintenance page).
- `styles/satchel.css`. Tests in `tests/` (no Foundry globals needed; the adapters test sets a fake `game`).

## Key patterns
- **Adapters read code, never guess.** Use only what a module exposes (its `api`, its settings menu, its settings). Each adapter function looks the api up at call time. A registration for the same id replaces the adapter entirely (`mergeEntries`). Adapters show only for installed modules; unknown modules only if they register.
- **Feature registry:** core's `createFeatures` (one world setting per tool, `feature-<id>`, requiresReload, `config: true`). Off = no buttons/hooks; API getters return undefined.
- **GM only:** every window, click handler and API entry that does something checks `game.user.isGM` (`api.entries()` too since 0.5.0: nothing outside the hub reads it on a player's client; the known modules only call `register()`); adapters never call another module's API on a player's client (Ringmaker, Loot Ledger, Red Book APIs are GM-only). No socket. Automatic writes (0.5.0): only the GM-only journal (first-seen versions, the version-change backup, the updates-found backup), only on the active GM's client (`Store.isWriter()`, Foundry's `game.users.activeGM`; no core leader needed since nothing is relayed). Everything else (imports, debug switch, cleanup, dismissals, Fix buttons, Back up now) is a GM click.
- **GM-only data** goes in the store journal (`Store.update(fn)` with a pure `fn` from store-model), never in world settings or flags players can read. A new field goes in `normalizeStore` (bump `STORE_VERSION` + an upgrade step when the shape changes).
- **Backup load order:** `setup` hook reads (SettingsIO.build reads every Satchel-read module synchronously before its first await; keep it that way), `ready` writes. Documented limit: `init`/`setup` changes, Foundry's own migration, modules with their own `exportSettings()` (asked after).
- **Health fix contract:** a line's `fix` (function / action id / `{ label, run | action, confirm }`, core's `readFix`, re-exported by health-model.mjs since 0.6.0; `FIX_ID` = core `FIX_ACTION_RE`) gets a `key` "section:line" (`keyFixes`); the hub's `healthFix` action finds it again in `Health.latest()` (`fixOf`) and runs it through `Self.runFix`, then re-checks that module. Registration `fixes: { id: fn }` (ids `FIX_ID`, `satchel:` reserved). Fix buttons only in the hub (`healthHtml({ fixes })`), never on the chat card. Lines without a fix keep the old shape.
- **Health time limits** live in `health-model.mjs`; never go back to one fixed short limit (the toolkit's first run after load is slow). The runner calls `runOne(entry, { limitMs })`; `checkOne` passes `health({ timeoutMs: moduleBudget(limitMs) })` (limit less ≤2 s) so a module's own per-part limits agree with the Satchel's (0.2.1).
- **Never throws into the hub:** health checks are wrapped and time-limited; update checks return `status: "error"` instead of throwing; settings reads report per module.
- **Settings keys stable** (never rename). Our settings: the feature switches, `debugLog`, client `showModuleData` (0.6.0) and core's client `windowPlacement`. Record-type settings of other modules go in `SKIP` (adapters-model.mjs) or the registration's `skipSettings`; core 0.5.0's client records `showModuleData` / `windowPlacement` are in every `SKIP` list and added to every entry by `settings-model.mjs` `skipList(entry)` (`CORE_RECORDS`; export, preview and apply all use it).
- **Module data folder (0.6.0):** core hides it unless ANY active module's `<id>.showModuleData` is on. The Maintenance page writes only our own switch (`data-change="showModuleData"`) and lists every other module's as read-only lines (`dataFolderRows()` in hub.mjs). Not secrecy: say so wherever it is described.
- **Windows (0.6.0):** placement is core's (`windowPlacement`); Maintenance › Reset window positions = `resetPlacement(ID)`.
- **Flags/storage:** only `flags.wanderers-satchel.*` (health chat cards; the store journal's `storeEntry` + `store` + core's `dataFolderFiled`; core's "Module data" folder, shared, no flag), session-storage keys `wanderers-satchel.update.*` and the local-storage keys `wanderers-satchel.healthFilter` and `wanderers-satchel.updateCheckedAt`. Cleanup (`cleanup.mjs` `plan`/`remove`/`CATEGORIES`: messages, store (unticked by default; `Store.remove()` also removes the folder when empty), cache, settings (walks every registered setting of our namespace, so client `showModuleData` / `windowPlacement` too)) must cover anything new.
- Windows are ApplicationV2 with HTML built in code (pure builders in `hub-view.mjs`), class `ws-window` (no backdrop blur). Clicks via `data-action` + `DEFAULT_OPTIONS.actions` (static private handlers, `this` = the app); changes (checkboxes) via one `change` listener on `data-change`.
- **Styling: core's shared look** (`vendor/wanderers-core/styles/wanderers-ui.css`, listed first in module.json `styles`; core docs/ui.md). Windows carry `...UI_CLASSES` (hub, health window); the chat card is wrapped in `View.ROOT`. Use core's classes and helpers (`wc-shell/side/nav/main`, `wc-pagehead`, `wc-stats`, `wc-panel`, `wc-banner`, `wc-alert`, `wc-table-box`/`wc-table`, `wc-btn*`, `wc-badge`, `wc-dot`, `wc-status`/`wc-lines`, `wc-val`, `wc-hint`, `wc-row`, tones `wc-ok` …; `navItem`, `badge`, `dot`, `icon`, `statusLine`, `TONES`, `tone`) wherever they fit. `satchel.css` holds only Satchel-specific rules (`ws-*`: tool cards, module/import tables, filter chips, health report groups, chat card sizes, transfer tabs, sticky footer, maintenance), reading core tokens (`--wc-*`); never copy a core component into it. Narrow layout for the Satchel's own grids via its own container `ws-hub` on `.wc-shell` (not core's revisioned name). Hex only as var() fallbacks.
- **Core stylesheet revision:** core 0.5.0 is class revision `wc-r3`; the Satchel hard-codes no revision (it uses `UI_CLASSES` / `View.ROOT`). The 0.3.0 `flex-shrink` override was dropped in 0.4.1.
- **Health filter:** `filter-model.mjs` (pure: keys ok/warn/bad/pending/off, `toggleFilter`, `filterChips` (totals), `applyFilter` (matching lines, hidden module count)); `prefs.mjs` keeps it in localStorage `wanderers-satchel.healthFilter` (every access in try/catch; cleanup category `cache` clears it). The hub's `healthFilter` action; the chat card and the separate health window show static badges.
- **Keyboard rules (0.4.1):** Foundry's core Space keybinding (pause) listens on the document, so the hub root handles keydown and keyup for every focusable control (`hub.mjs` `#onKeyAny` -> `hub-model.mjs` `hubKey`): Space and Enter stop propagation. Native controls (buttons incl. sidebar links, filter chips, tabs; links; fields) keep the browser's own single click (no preventDefault); a non-native control (role=button or data-action) gets Space turned into one click on keydown, none on auto-repeat. Chips are plain native buttons using the `healthFilter` action (no special key code). Sidebar arrows/Home/End stay in `#onKey`. Focus: after opening a page from a sidebar link with the keyboard, focus stays on the sidebar link of the page now shown (`_replaceHTML` restores it; chosen over moving focus to the page heading so arrow keys keep working).
- **Other modules' setting labels** go through `settings-model.mjs` `label` / `localizeDefs` with `game.i18n.localize` passed in (settings-io.mjs `defs`), so translation keys never show raw.
- Pure files have no Foundry calls at import time and are tested in Node.

## What the adapters assume (check when those modules change)
- Toolkit: `api.panel(tab)`, `api.healthReport({ timeoutMs })` (1.27+, core report, no card; 1.27.1+ honours `timeoutMs` per section; falls back to `api.health()`), `api.cleanup.open()`, setting `debugLog`. `api.settingsIO` only on old versions (1.27 drops it). No Session Start / Who's online use (1.27 removed Who's online; `onlineHudPos` stays registered hidden only for Red Book's move). `api.settingsRecords()` (1.27+) lists extra record settings; the adapter's `skipSettings` adds them on a GM client (`skipFor`), static `SKIP` as fallback. The `flightNetwork` setting now holds only the players' view `{version, points, routes}`; the full network is in the toolkit's GM-only store, so an import does not restore locked points.
- Ringmaker 1.5.0: GM-only `api.status()`, `api.removePlan()`; menu "Ringmaker tools"; world setting `debugLog` (added in 1.5.0; on 1.4.x the debug row says the version has none). `changelog: CHANGELOG.md` in its manifest (What's new reads it).
- Loot Ledger 0.3: no API calls; reads `world.loot-ledger-items` / `-converted-items` / `-tables`, journal flag `flags.loot-ledger.buildReport`, the required module's Item packs, settings `convertOnBuild` `reviewBoard` `qualityColours` `randomSuffixes`.
- Red Book 0.4.0+ registers itself with the Satchel (`registerWith`, at once and again on `wanderers-satchel.ready`), which replaces the adapter: `openPanel`, `health({ timeoutMs })`, `debugSetting` `debugLog`, `skipSettings` = its hidden records. The adapter stays for 0.3 (api set in its `ready`): `api.panel(tab)`, `api.health()` (array of lines), `api.cleanup.open()`, setting `debugLog`; skip list `openSession` `boardPins` `onlineHudPos` `onlineHudCollapsed` (client, 0.4.0) `migrations` `nextSession`.
- Suggested in those modules (not done here): `debugLog` in Loot Ledger; `fix` actions on their health lines (README *Health lines with a fix*); a `changelog` entry in the toolkit's, Loot Ledger's and Red Book's manifests (without one What's new falls back to GitHub releases).

## House practices
- **Release tags** are `vMAJOR.MINOR.PATCH` only (`v0.1.0`). The Release workflow fails early on anything else and sets version/URLs from the tag.
- **Compatibility:** `module.json` `compatibility` minimum 13, verified = newest Foundry checked live (14.369), no maximum. No `relationships`: system-agnostic, and the modules it knows are optional.
- **Docs:** README *Public API and hooks* lists every `api.*` entry and the hook, each stable or experimental. Update it with any API change.
- **End each release with a live checklist** in the changelog: what was not run in Foundry.

## Tests
- `npm test` = `node --test tests/*.test.mjs`; `npm run check` syntax; `npm run lint` (core's ESLint config); `npm run types` (tsc on JSDoc). CI = core's reusable `module-checks.yml@v0.5.1` (pin check, then all four); the Release workflow verifies the pin and runs check + test again.
- Updating core: `node vendor/wanderers-core/vendor.mjs update X.Y.Z` (behind the agent proxy: `NODE_USE_ENV_PROXY=1 NODE_EXTRA_CA_CERTS=/root/.ccr/ca-bundle.crt`), bump the workflow tag, never hand-edit `vendor/`.
- Tested (0.6.0, `tests/v060.test.mjs`, on core's fakes `vendor/wanderers-core/testing/`, tests only): store found by `storeEntry` and filed once (a GM's later move kept), players read nothing / can't write, `remove()` with the empty folder, `status().playersCanSee`, cleanup plan of the client records, `dataFolderModel` + Maintenance HTML (escaping, one control), `CORE_RECORDS`/`skipList`, core `readFix`/`FIX_ACTION_RE`, source checks (RememberedWindow on both windows, key binding id `open` without `editable`, `hideDataFolder`, `Store.file()` on the writer).
- Tested (0.5.0, `tests/qol.test.mjs`): manifest fallback, store normalizer/caps/changes/snapshots, update-set key, notes source/changelog parsing/ranges/releases/fetch failures, Markdown escaping (no tags, no javascript: links, balanced lists, cut), fix contract (readFix, keys, findFix, registration `fixes`), Fix buttons (hub only, escaped), Satchel's own lines, backups page/router/model, What's new cards, banners, `entries()` GM gate and cleanup coverage (source checks).
- Tested: hub router, sidebar keys, health index/dots/badges, update view, nav/overview/module/import models, view HTML (escaping, actions, no status characters), version compare, update source, update check (cache, failures, timeout), registration reading, merge, card model, doc links, debug plan, health normalising, time limits, parallel runner (slow/timeout/late/throw), grouping, settings bundle, per-module validation and validators, plain-data check, write-time recheck, adapters against a fake `game` (including no API calls for players), health filter (toggle, chips with totals, matching lines, hidden count, stored text), filter/report/card HTML, setting label localizing, prefs storage (missing or throwing storage).

## Release process
1. Bump `version` in `module.json` and the `download` URL (`.../releases/download/vX.Y.Z/module.zip`); manifest URL stays `.../releases/latest/download/module.json`.
2. Add a `CHANGELOG.md` section with an "Untested in Foundry" checklist.
3. Commit and push to main. **Agents never tag or publish.** The user publishes the GitHub release; the Release workflow runs tests, sets version/URLs and uploads `module.json` + `module.zip` (`module.json scripts styles vendor README.md CHANGELOG.md LICENSE`, minus `vendor/wanderers-core/config/`, `vendor/wanderers-core/testing/` and `vendor.mjs`). A new top-level folder must be added to the zip step.
